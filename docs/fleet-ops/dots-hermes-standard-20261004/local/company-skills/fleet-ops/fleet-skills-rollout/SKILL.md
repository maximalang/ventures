# Fleet Skills Rollout

Как отбирать и раскатывать агентные скиллы из Skills Hub по профилям флота. Скиллы ставятся в профиль флота — воркеры канбана видят только скиллы своего профиля.

## Отбор качества (до установки)

1. `hermes skills search "<query>" --limit N --json` — несколько запросов, дедупликация по владельцу/репо.
2. Качество смотреть на `https://skills.sh/<owner>/<repo>/<skill>`: installs, GitHub stars, security audits (Trust Hub / Socket / Snyk). Ориентир: десятки тысяч установок + живой репо.
3. Отсев: пустые скиллы без содержимого, клоны, скиллы только под платные инструменты (Ahrefs/Semrush/DataForSEO и т.п.) без бесплатного пути.
4. Предпросмотр контента: `hermes skills inspect <source>/<owner>/<repo>/<skill>`.
5. Проверить состав всего пакета на странице репо: часто нужен не один скилл, а согласованный набор.

## Установка в профиль флота

```bash
hermes --profile <name> skills install <source>/<owner>/<repo>/<skill> --yes
```

PITFALL: переменная окружения `HERMES_PROFILE` НЕ маршрутизирует установку — только флаг `--profile`.

Длинные батчи (5+ скиллов × несколько профилей) упёрся в потолок 600 с форграунд-терминала: запускать `terminal(background=true)` и ждать через `process(action='wait')`.

Верификация: `hermes --profile <name> skills list` — скилл `enabled`.

PITFALL: `skills list` рисует широкую таблицу и ОБРЕЗАЕТ колонку Name многоточием (`fleet-browser-routi…`) — grep по полному имени скилла ложно даёт пустой результат при установленном скилле. Грепать короткий уникальный префикс имени.

PITFALL: exit-код `hermes skills install` не информативен — ошибка "Could not fetch ... from any source" тоже возвращает 0. Верифицировать всегда по `skills list`, никогда по exit-code.

PITFALL (Windows): фронтматтер `platforms: [linux, macos]` без `windows` → скилл ставится в папку профиля, но МОЛЧА не появляется в `skills list`. Симптом: установка «успешна», папка на месте, в списке пусто. Фикс: прогнать скрипты скилла на хосте (смоук-тест) и добавить `windows` в `platforms` патчем (пример: официальный `watchers`, 01.09).

## Триаж сканера skills-guard-v2

При блокировке перезапустить установку и читать полный отчёт (строки после `Scan:` — там сами findings). Частые ложные срабатывания:
- `context_exfil` — строка в тестовых фикстурах (например, в `evals/evals.json`);
- `traversal` — относительные markdown-ссылки вида `../../../tools/...` в документации;
- `injection` — HTML-комментарий со статистикой.
Если находка — контент фикстур/документации (не код и не команды) — ставить с `--force`. Dangerous-вердикт не форсить.

## Обход сбоя хаб-фетча

Если `hermes skills install` даёт "Could not fetch ... from any source", но репозиторий доступен: скачать вручную в `<profile>/skills/<name>/`:
- `SKILL.md` — `https://raw.githubusercontent.com/<owner>/<repo>/main/skills/<name>/SKILL.md`;
- список `references/` — через GitHub API `contents/skills/<name>/references`;
- каждый файл из `references/` — тем же raw-путём. Проверить листинг и целостность.

## Интеграция внешнего знания (owner прислал репо/каталог: «интегрируй агентам»)

1. Источник забирать ПОЛНОСТЬЮ: `curl -sL <raw-file-url> -o scratch && wc -c` — web_extract режет большие README серединой списка, а дистиллят требует весь документ; сверить байтовый объём с источником. Аффилиат/реферальные коды из ссылок вычищать.
2. Новый скилл НЕ создавать: дистиллят — в `references/<topic>.md` канон-скилла, УЖЕ раскатанного на целевые профили (для браузера/stealth — fleet-browser-routing), + указатель 2–3 строки в SKILL.md с формулой «загружать когда».
3. Обязательный состав дистиллята: (а) mapping внешних инструментов → существующие линии/capabilities флота («что уже есть»); (б) порядок внедрения новых бесплатных инструментов: external-asset-vetting → изолированный смоук на проверочных тестах → evidence-нота → линия; (в) жёсткие policy-гейты тремя корзинами — автономно разрешено / owner+finance-гейт / запрещено — на основе уже существующих разрешений (tick-only капча, телефон/SMS-потоки, лимиты spend и outreach Fleet Policy). Расширять разрешения через дистиллят нельзя; платные сервисы — каталожно, без подписок.
4. Выбрать режим по точному scope: новая reference + hook → scoped additive rollout с сохранением каждой прежней версии SKILL.md; полная синхронизация дерева допустима только при отдельном разрешённом whole-skill scope (см. «Обновления»). Для additive rollout сверять одинаковые bytes новой reference, один hook и равенство root-minus-hook собственной raw backup; не выравнивать целые корни ради md5=1. Подробности: `references/scoped-additive-rollouts.md`.

## Аудит дублей (после раскатки)

Точные коллизии имён: воркер грузит только одну копию, вторая молча игнорируется. Метод: для каждого профиля `find "$LOCALAPPDATA/hermes/profiles/<p>/skills" -name SKILL.md`, вытащить `name:` из фронтматтера (или имя папки), `sort | uniq -d`. Коллизии 01.09 (content-strategy, test-driven-development, performance-optimization) и семантический конфликт `ai-seo` (рекомендует `llms.txt`) vs `seo-geo` (миф-бастит его по гайду Гугла) задокументированы в `references/marketing-skills-stack.md` («Аудит дублей»). Семантические конфликты (противоречащие рекомендации в разных скиллах одного кластера) искать отдельно от коллизий имён — сравнивать тела, а не только имена.

## Чистка незарегистрированных skill-директорий (проверено 04.09)

Под `profiles/<p>/skills/<category>/` накапливаются суб-директории, скиллы которых НЕ зарегистрированы в профиле (импорт-бандлы из других тулов, остатки удалённых профилей — пример: 18 мёртвых суб-скиллов в `codex-imports` профиля company). Дерево решений:
- `hermes --profile <p> skills list` (или листинг зарегистрированных) — зарегистрировано+enabled = живое, НЕ трогать;
- незарегистрированная или disabled директория — кандидат на диагностику, НЕ автоматически мусор: проверить platform-фильтр, manifest/enablement, ссылки из других скиллов, задач и cron, сезонные применения и полезную уникальную процедуру;
- перед удалением верифицировать остающиеся живые скиллы по хэшу ключевых файлов — бэкап не страхует от собственной ошибки при выделении мусора;
- та же категория в ДРУГИХ профилях может быть легитимно зарегистрирована (в 6 профилях по 30–33 `codex-imports` зарегистрированы и enabled — оставлены): вердикт выносится ПО-ПРОФИЛЬНО, не слепым проходом по флоту.
Удалённые скиллы могут ссылаться на живые зонтичные (sub-скиллы автономны) — проверять, что зонтик ничего не импортирует из удаляемого, иначе чистка ломает живое.

## Откат раскатанного скилла (владелец отклонил подход)

- `skill_manage delete` удаляет только каноническую копию АКТИВНОГО профиля. Раскатанные по другим профилям директории удаляются файлово в каждом профиле (`profiles/<p>/skills/<category>/<name>/`), затем readback `hermes --profile <p> skills list` на каждом (grep по короткому префиксу имени = 0).
- Манифест фиксируется ЕЩЁ при раскатке: список профилей + пути копий + сопроводительные артефакты (скрипты в tools/, тест-фикстуры) — откат механический, не по памяти.
- В тот же проход правится слой знаний, кодифицировавший отклонённый подход: записи fact_store ОБНОВЛЯЮТСЯ (фиксация отклонения, чтобы подход не предложили снова, а не просто удаление), плюс specs и припаркованные карты со ссылками на него. Иначе следующая сессия воскресит отклонённый вариант из собственной памяти.
- Сопутствующие тулы/скретч-артефакты удаляются вместе со скиллом; верификация — листингом путей, а не успехом delete-вызова.

## Карантин zero-use скиллов по флоту

Класс: профили обросли сотнями ни разу не загруженных скиллов (bundled-сид + хаб); цель — снять их из индекса системного промпта и с диска, обратимо.

1. **Usage — неполный сигнал, не критерий удаления.** Нулевое использование не доказывает бесполезность: могут не учитываться инъекции, cron, прямые чтения и редкие аварийные задачи. До карантина сопоставить purpose, регистрации, ссылки и фактические владельцы процедуры. Только в разрешённом профиле проверить доступные ссылки из задач/cron; не читать чужие хранилища ради этого аудита.
2. **Protected-allowlist**: safety/discipline/гейтовые скиллы (worker-tool-discipline, fleet-doctrine, security-*, evidence/gate-скиллы) не трогать даже при zero-use — они грузятся инъекцией, а не через skill_view, и в счётчик не попадают.
3. **Разделить bundled и не-bundled**: bundled (имя есть в `skills/.bundled_manifest`) мало перенести — `hermes update` пересидирует их обратно (чистка откатится = дрейф). Для bundled: перенос + маркер `.no-bundled-skills` В КОРНЕ ПРОФИЛЯ (`profiles/<p>/.no-bundled-skills`, НЕ в `skills/` — путь резолвится от `_hermes_home()`, маркер внутри skills/ не работает). Обратный ход — `hermes --profile <p> skills opt-in`.
4. **Cross-ref проверка до переноса**: grep по телам ОСТАЮЩИХСЯ SKILL.md на имена кандидатов — живой скилл не должен ссылаться на уезжающий.
5. **Обратимый карантин, не обход политики:** до переноса нужны независимые backup/scope evidence, разрешённый профиль и точный dry-run manifest. Способ файловой операции не меняет полномочий. Сохранять hash manifest и rollback; не переносить скилл только потому, что move технически проходит, а delete запрещён.
6. **Пост-верификация**: `hermes --profile <p> skills list` (enabled-счётчики), cron-ссылки резолвятся, нужные скиллы на месте. Битые ссылки, существовавшие ДО чистки, — не повод откатывать; передать в контур-аудит.

## Новый профиль-специалист (роль отдела) — полный порядок

Класс задачи: владелец требует в отделе профессиональных ролей (режиссёр, монтажёр), а не универсальных агентов.

1. `hermes profile create <role> --clone-from <ближайший по модели> --no-alias --description "..."` — клон тянет config.yaml + .env (ключи рельсов) + skills; `--no-alias` не плодит wrapper-скрипты. Модель наследуется от источника: креативные роли клонировать от sol-профиля, технические — от glm-профиля.
2. Переписать `profiles/<role>/SOUL.md` ПОЛНОСТЬЮ (write_file откажет без предварительного read_file клонированного файла): ремесло, зона ответственности, рабочий цикл, «не твоя зона», handoff-контракт, Fleet Policy Gate.
3. Авторские скиллы-плейбуки профессии создаются `skill_manage` В АКТИВНОМ профиле (company) — другого пути нет; затем каталог копируется в целевой профиль (`profiles/<role>/skills/<category>/<name>/`) и верифицируется `hermes --profile <role> skills list` → `enabled`. Копия директории = рабочая установка локального скилла; hub-скиллы ставь штатным `skills install --profile`.
4. `hermes profile describe <role> --text "..."` — описание читает оркестратор канбана при выборе assignee.
5. Занести роль в канон отдела (ростер + кто за что отвечает) и в профильный орг-скилл.
6. Пробный прогон на реальной задаче под наблюдением; роль, не превзошедшая универсала за 2 цикла, удаляется (`hermes profile delete`), задачи возвращаются базовой роли. Ростер не раздувать заранее — нового спеца создаёт триггер (системный дефект ≥3 раза / поток задач из ≥2 источников / перегруз), а не «на вырост».

Воркер канбана поднимается по имени `assignee` лениво — новый профиль не требует резидентного гейтвея.

## Обновления

`hermes skills check` / `hermes skills update` — для хаб-установленных; вручную докачанные скиллы обновлять повторной закачкой с того же источника.

Операционные уроки массового `skills update` (01.09/02.09):

- **Питфолл вечного `update_available` на Windows (проверено побайтово):** инсталлятор хаба пишет файлы на диск с `CRLF`, апстрим-бандл хэшируется по `LF` — содержимое побайтово идентично, но `content_hash` в `lock.json` не совпадает с фетчем, и `check` после УСПЕШНОГО обновления снова показывает все скиллы как `update_available`. Диагноз: `disk_len - fresh_len == число_строк` для отличающегося файла + первый дифф на `\r\n` vs `\n`. Не гонять повторные апдейты на основании этого статуса — сверять содержимое, а не хэш.
- Батч по флоту — только фоном: `for p in <profiles>; do hermes --profile $p skills update; done` в `terminal(background=true)`; каждый профиль тянет каждый скилл по сети, ~минуты на профиль. Ждать через `process(action='wait')`.
- Скиллы с локальными правками НЕ затираются: вывод «kept your local edits: <name>» (пример: `fleet-doctrine` с патчами флота). Форс-перезапись — только `hermes skills update <name> --force` осознанно.
- **Синхронное обновление авторских скиллов по профилям** (копия канона company → воркер-профили, уже держащие устаревшие копии): сначала бэкап каждой целевой директории в scratch (обратимость), затем копировать канон ЦЕЛИКОМ — SKILL.md + подкаталоги references/ и scripts/ (частичная копия оставляет устаревшие extras, на которые ссылается новый SKILL.md), верифицировать по content-hash всех файлов (mtime копируется вместе с файлом и ничего не доказывает), затем `hermes --profile <p> skills list` → enabled. Копии в профилях дрейфуют молча (воркеры патчат свои) — при рассинхроне сверять ВСЕ профили, держащие скилл, и диффить содержимое перед перезаписью, чтобы не затереть чужую более свежую правку. Критерий безопасной перезаписи: diff канон→копия даёт только строки удаления (`<`) и mtime канона новее = канон строгий суперсет; любая `>`-строка — чужая правка, мержить вручную. После ЛЮБОЙ правки канон-скилла в company в тот же проход находить все копии (`find profiles/*/skills -type d -name <skill>`) и синхронизировать: дрейф невидим, пока воркер не примет решение по устаревшему канону. Быстрая проверка синхронности: `md5sum` по всем копиям SKILL.md → `sort -u | wc -l` = 1.
- Обновление перезапускает security-скан: ранее поставленные через `--force` скиллы (ложные `context_exfil`/`traversal`/`injection`) уходят в `.hub/quarantine` и пересканируются. После апдейта проверить, что они вернулись на место и карантин пуст, иначе повторить установку с `--force`.
- `hermes skills update` без аргументов = все хаб-скиллы профиля; точечное — `hermes skills update <name>`.

Кураторский стек маркетинг-скиллов и карта раскатки по профилям: `references/marketing-skills-stack.md`.

## Периодический аудит флота (скиллы + плагины + MCP)

Полный чеклист с готовыми командами: `references/fleet-audit-checklist.md`. Класс задач: «проверь скиллы/плагины/MCP у ботов», пост-миграционные ревизии, аудит после массовых апдейтов. Ключевые пункты:
- платформенно-мёртвые скиллы (`platforms:` без `windows` — молча не грузятся, один рекурсивный grep на весь флот);
- плагины живут либо в `<profile>/plugins/`, либо как pip-пакеты в site-packages venv — отсутствие папки в профиле не значит «не установлен»;
- MCP живость: 401/405 от `curl` = сервер жив; ключи окружения проверять только на наличие (`${!k}`), никогда не читать значения;
- осиротевшие скиллы после удаления профилей (ссылки на несуществующие сущности в `description:`);
- пустые `.install-*` в `plugins/` = прерванная установка; плагины без ключей (например langfuse) выключать до триггера.
Аудит только читает; правки конфигов — после команды владельца. Рецепты фазы правок (бэкапы, перенос папок скиллов, патч фронтматтера, валидация YAML, питфолл бэкслешей в bash-циклах) — в чеклисте, раздел 7.

## Применение подготовленного пакета по манифесту (manifest-driven apply)

Класс: готовый пакет изменений скилл-файлов (payload операций + манифест `before_tree`/`candidate_tree` с хэшами) применяется живой сессией через `skill_manage`.

- До применения сверить якоря: все нетронутые файлы совпадают с `before_tree`, все строки payload — с `candidate_tree`, новые пути отсутствуют. Расхождение якоря = пакет устарел, не применять.
- После применения сверять КАЖДЫЙ изменённый файл побайтово с хэшем манифеста. Единственный допустимый эквивалент — отсутствующий финальный перевод строки (writer-форма `skill_manage write_file` может не дописать последний `\n`/`\r\n` источника); любой другой diff — реальный дефект, а не «норма переносов».
- Большой payload, заново набираемый инлайн в tool-вызовах, молча теряет строки/блоки. Не патчить вслепую: diff (difflib) против эталона, затем полная перезапись файла `write_file` с корректным содержимым — точечный patch по `old_string` на уже нормализованном файле часто не матчится.
- Нетронутые файлы манифеста сверять так же: пакет обязан не менять ничего вне своего списка.
- Итог — receipt-файл вне scratch (перечень операций, хэши до/после, sha256 самого receipt), чтобы воркер/аудит мог сверить живое состояние без повторного применения.

## Аудит качества контента (описания/ссылки/размеры)

- Зафиксировать root, регистрации, полный файловый manifest и проверяемый backup ДО смыслового аудита. Покрытие считать по уникальным путям, не по самоотчёту агента.
- Разделять инвентарную проверку всех файлов, смысловое чтение корней и выборочную проверку references; не выдавать последнюю за exhaustive-аудит supporting files.
- Перед применением сверять exact old bytes/current hash. При параллельном переносе не следовать за файлом в другой профиль и не воскрешать удалённую копию; сохранить scoped pending patch.
