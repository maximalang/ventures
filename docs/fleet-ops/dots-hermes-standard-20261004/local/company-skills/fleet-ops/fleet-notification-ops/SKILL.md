# Fleet Notification Ops

Keep owner-facing delivery limited to decisions and material incidents without hiding failures. Load only the reference for the current action.

## Unified owner outbox (22.09 canon)

ALL owner-facing auto messages flow through ONE outbox — `profiles/company/scripts/owner_inbox.py` (JSON queue + file lock):

- Producers (watcher scripts and agent crons) NEVER print to TG stdout and never call `hermes send`. Script jobs: `deliver=local`, call `owner_inbox.push(lines, level, key)`. Agent crons: final response `[SILENT]` + push via `python scripts/owner_inbox_push.py --level <lvl> --key <k> --html` (HTML on stdin). A NEW producer lane is level=internal by default: a dry-run/stats lane pushing at info level spammed the owner hourly — before enabling any cron that pushes to owner_inbox, grep the script's push level; owner-visible is only for a human action-needed line. Immediate noise kill-switch: `hermes cron pause <job_id>` (CLI verbs are pause/resume; cronjob_manage has no disable action) — pause first, fix the level through the staged tech→QA→activation chain, re-enable only after a dry tick proves owner-silence.
- OWNER-VISIBLE PUSH SIZE LAW (owner escalations 30.09 «большая и непонятная», 01.10 «что за каша»): any push with level normal/info destined for the owner is ≤6 lines of human language — what changed, what it means, next step, owner action (or «не требуется»). FORBIDDEN in owner-visible text: defect enumerations, SHA/hash re-verification narratives, acceptance/independence internals, run/session numbers, multi-paragraph campaign chronicles. That detail belongs in the Kanban card/ledger AND (when the owner must be able to see that kitchen exists) in a level=internal push or one summary line («починка X: приёмка не прошла, переделка идёт, действие не требуется»). A long result report = ONE line + pointer to the card/artifact. Rule for every producer lane (watchers, crons, worker handoffs, company sessions alike) — the flush renders pending events verbatim, so a wall pushed at normal level arrives as a wall. DEV-JARGON BAN in owner-visible text: git/CI/infra vocabulary (ветка, слияние/merge, rebase, CI, workflows, мейнтейнер, SHA/хеш, коммит, деплой, exact-head, run, гейт, печать, pid, traceback, English tool statuses) never reaches the owner — translate to human equivalents («слияние с основной веткой» → «обновление принято и выкатывается»; «ждёт одобрения мейнтейнера / CI внешнего проекта» → «обновление отправлено авторам внешнего проекта, ждём их ответа»; «RuntimeError: HTTP 403» → «сбой инструмента — компания чинит»). Money: ONE aggregate line only when there is real movement (non-null, non-zero); enumerations of null financial articles are forbidden noise. Enforcement lesson (owner complained three days running while each fix only patched the current offender): per-producer prompt edits are whack-a-mole — new producers and drifting prompts re-inflate the digest; enforce the cap MECHANICALLY at the single entry point (owner_inbox.push / flush render: owner-level events >6 lines get trimmed with a pointer, full text stays in the journal, critical is never truncated), and treat any owner verbosity complaint as a trigger to check the choke-point, not just the latest message.
- The ONLY sender is cron `owner-inbox-flush` (job a06c7e0509d8, every 10 min, `owner_inbox_flush.py`, deliver=telegram:-1004426332349:281 — notifications thread «Вести» of group «𝗕 🌐 и CX»; full route map → `references/cx-group-routing.md`).
- The stock cron envelope is DISABLED fleet-wide: `hermes config set cron.wrap_response false` (direct patch of config.yaml is blocked as security-sensitive; use the config CLI). Without it, every cron delivery would arrive wrapped in `Cronjob Response: <name>` + job_id + «Управление: stop reminder …» around the script's own rendered message — fleet scripts render owner text themselves (tg_format.LORD). Editing another profile's jobs: `hermes -p <profile> cron edit <id> --deliver …` (profile alias wrappers may not be on PATH in MSYS shells).
- Levels: `critical` (owner-boundary decisions, watchdog-path failure) — sent immediately, max 1 msg per flush; `normal` — batched, min 2 h gap; `info` — only rides along with a normal/critical flush or the morning dump after quiet hours; `internal` (owner 29.09: fleet kitchen is noise to the owner) — journal-only, NEVER owner-rendered: policy/deny producers (`fp-notify`, `deny-triage`) push internal exclusively, and the flush also filters these KEYS at any level so their legacy normal/info events are swept too (the critical path bypasses the key filter — a genuine breach still fires). Company reviews the internal journal itself and converts the rare genuine owner-boundary item into an `owner-ask` event (source_meta «🔴 Нужно ваше решение»). One assembled message: critical first, then normal, then info, ≤4000 chars.
- Hourly work rollup (owner directive 23.09 — «если пусто, сделай сборку по всем работам и что ждёт моего решения»): a daytime tick that produced NO message AND ≥60 min since any owner message (anchor `max(last_digest_at, last_rollup_at, last_msg_at)`) sends 🧾 «Сборка работ» — live kanban sweep via `fleet_rollup.py` (read-only `hermes kanban … --json`, never direct DB): active tasks, board counts, owner-decision items. Journal cursors are NOT consumed (pending info still waits for the next real грамота); every sent message including critical updates `last_msg_at` and resets the anchor. Details → `references/owner-inbox.md` rule 5. The rollup carries a «Завершено» section (owner 27.09 «где результаты… не дошли в чат»): a done-pool vs `done_seen`-cursor set-diff shows completions since the last PRINTED rollup — a completion is a silent event and neither board threads nor the digest surface it otherwise. Set-diff against a persisted cursor, NOT a time window, because kanban `completed_at` does NOT refresh on re-completion — a re-run card keeps its first completion epoch and any window filter silently misses it (verified live); advance the cursor only on an actually printed rollup so an unprinted check never consumes the window, and seed it silently on first boot to avoid a flood of old done cards. Wording rule: the owner reads a bare «в очереди N» as N undelivered MESSAGES — label kanban counts as cards («карт в очереди»), and when asked «сколько вестей в очереди» answer the message-queue (journal pending) and the card-queue separately. Owner directive 30.09 (literal naming, issued after the owner twice challenged rollups that showed queued cards as work): the work section is named «Выполняется» and lists ONLY genuinely executing cards (running/review, each with last-event age); queued cards (ready/scheduled) belong under a separate «Очередь» header — folding the queue into a work label inflates the picture of live work and provokes owner distrust. Render status sections ALWAYS, even empty («Выполняется: — нет»): a section that disappears when the fleet is idle reads to the owner as a broken report (owner: «где раздел выполняется?»), while an explicit empty placeholder states the true condition and prompts the honest follow-up (why idle — wave finished, quota park, stall) in the same message. OWNER RENDER LAW (03.10, after repeated «внешний вид грамот опять непонятный; заголовки и текст непонятные»): in every digest section EACH card is its OWN blockquote block (icon + human board name + title + one status/freshness line) — never a merged common list; digest headers carry ONLY the gramota type («Сборка работ», «Грамота получасовая», «Утренняя грамота — вести за ночь») with NO date/time stamp (timestamps stay in the journal); owner-visible cron/agent output is HTML-only — Markdown ** asterisks render literally through the flush HTML path (agent prompts drift to asterisks even when the template shows <b> — ban them explicitly in the prompt), and null / BLOCKED / rc= / SHA tokens are banned jargon («нет данных», «задержано до независимой приёмки»). Cards complete within minutes of any snapshot: when the owner questions a rollup's counts, re-run a live per-board census (stripped-env child) and answer with current statuses plus what changed since the snapshot — never defend the stale printout. When the owner asks what the «Внутренние проблемы: N» line contains, decode it from the internal-journal tail (level=internal entries, fp-notify/deny-triage keys) cross-checked against the policy CLI's read-only `status` counts (pending approvals/notifications), and answer one human line per item together with the company action already taken — the line is a COUNT of kitchen events, not one problem, and answering it from the rollup text alone is always wrong.
- A push QUEUES, it does not send: verify by reading the journal tail (`owner_inbox_journal.jsonl` — your key, level, `sent=None`; entry CONTENT lives in the `lines`/`full_lines` fields, there is no text/html field), never by claiming delivery. When the owner calls a digest «непонятная», diagnose from the journal FIRST: pull owner-visible entries (level normal/info/critical) since the complaint window and group by `key` — the offender is almost always one specific producer key (a stats lane, a raw watcher dump, a duplicated halt alert), not the rollup renderer; the item leaves on the next flush tick (≤10 min, critical included). The push CLI reads its body from STDIN: a call with empty stdin exits 0 having written NOTHING (silent no-op) — workers that «sent» an escalation without a journal entry left owner-bound requests undelivered for hours. Always pipe the body from a file and treat a missing journal row as «escalation did not happen»: deliver it company-side yourself. BUT a missing journal row only proves the push did not go through owner_inbox — the same artifact may already have been delivered INTERACTIVELY (an agent reply with MEDIA attachments in the owner thread, or `hermes send` by a parallel session; neither touches the journal). Before re-pushing a «missing» delivery, verify the claim with session_search on the exact artifact filename (the sending turn's MEDIA lines are in the session log) — re-pushing an already-delivered pack double-notifies the owner. Until flushed, the queued row is still editable — fix typos in the stored lines and recompute `sig` (sha1 of the body, first 16 chars) so dedup matches the new text; after flush, corrections are impossible.
- Report briefs for PROPOSAL-class cards (research/review whose deliverable is a recommendation — model routing, policy, tooling) are DRAFTS until company posts a disposition on the card: the owner-visible brief carries the company verdict («предложение отклонено/принято, переработка запущена»), never the raw recommendation as an owner-approval touchpoint for routine matters — model/tech routing is a company decision; the owner sees only material boundaries. Cost words in a proposal («бесплатно», «дёшево», «не критично», token savings) are NOT quality evidence: reject and rework such drafts before they reach the owner (owner sequence: quality first → independent evidence → optimization only with demonstrated non-regression). Forwarding an unreviewed executor draft as an owner decision request is a company defect, not a delivery feature.
- Superseded escalation: dedup is by body-sig, not key, so pushing the SAME key with a corrected body queues a NEW event — use that to retract. Before briefing the owner on a shared package/decision doc, re-read it fresh: the owner edits these docs directly, and a brief quoting the pre-edit version (or recommending a step the owner already cancelled) misleads worse than silence. When your earlier queued/sent recommendation is overtaken by an owner edit or a completed work item, send a short correction under the same key that explicitly names what is retracted and what changed, not a fresh brief pretending the old one never existed.
- Exception: `gateway_watchdog.py` may `hermes send` directly — it fires only when the gateway (and thus the flusher's delivery path) is down; it IS the recovery probe.
- Reasons shown to the owner are passed through `owner_inbox.sanitize_reason()` — strips `pattern=`/`call_index=`/raw rule ids, maps rule_id → human Russian via `owner_inbox.RULE_RU`. Never show internal policy markers to the owner. Outbox pending-preview rows (`fleet_policy_notify.pending_preview`) translate classifier pattern ids via its `PATTERN_RU` lookup (an unknown free-text reason falls back to a generic Russian phrase, never raw English) and derive the required-action clause by cross-checking the row's task against the LIVE approvals table: live binding = «компания решит сама (отклонит/рескоупит) или переведёт в конкретную просьбу владельцу», else «запрос уже не активен — флот разбирает сам». These preview lines are INTERNAL journal text (all fp-notify/deny-triage output is level=internal since 29.09): protocol words («одобрить/отклонить t_xxx») may live there for company audit but must never reach owner-rendered sections. Never infer staleness from the payload's `action` field — it is the action TYPE («terminal» = a terminal command), not a status; reading it as «expired» labels live requests stale and stale ones live. The approvals count line must carry a per-binding preview built from the approvals table (card id + what the worker asks to do + exact answer words) — a bare «N просьб ждут печати» forces the owner to ask what is wanted from him.
- Rationale (owner 22.09, angry): 8 independent 5-min watchers each printed directly to TG → 11 confusing messages in one morning. Before adding ANY new owner-facing alert, extend an existing producer or push to owner_inbox; never wire a new direct TG route.

## Safety boundary

- Fleet-policy approve/reject owner boundary (owner directive 20.09, replaces the earlier owner-TTY-only rule): owner decides ONLY accounts/money/ownership/KYC-class items. Routine approval bindings (workspace-scoped cleanup, execute_code, git hygiene on a LIVE card) are resolved by company itself via the documented store call (`decide_approval(rule_key, <bool>, "company", confirm_code=rule_key[-8:])` from a shell with `HERMES_KANBAN_TASK` unset): approve live routine cards, reject bindings on done/archived cards, and AUTO-REJECT the worker-discipline classes — destructive-command, secret-store-access and policy-plane-probe denies (`COMPANY_RESCOPE_CATEGORIES` in deny_triage_bot): reject is the safe direction (protection stays armed), the card gets a rescope comment, and these are NEVER shown to the owner as seal requests (owner 29.09: a worker's invalid request is a card defect for company to re-scope, not an owner decision; presenting it forces him to decode «непонятно что»). Hold + escalate ONLY genuine owner boundaries: financial over budget, paid capability/payment rail, phone/KYC/domain/bank, mass outreach, legal/reputation, ownership/root, security-policy change — each escalated as a human «да/нет» ask (key `owner-ask`) in plain terms — never the approve/reject protocol tokens, which stay company-side. A genuinely needed destructive operation re-enters through a scoped evidence-gated card (backup+scope gates), never through an ad-hoc approval. Technical holds (lookup failures, unknown categories, exhausted retries) go to the internal-worklist line («компания разбирает сама, действие не требуется»), not the owner block. A stale binding that keeps re-reminding despite a provably DONE card is usually a board-label defect: the approval was recorded while the host carried a leaked board pin (label `default`), the auto-triage bot cannot resolve the card and HOLDs instead of rejecting stale — diagnose from `classes_seen` in its state file (`hold:board_unresolved`) and fix the bot's lookup (cross-board scan proving done/archived before the sanctioned decide call), never the guard. Undeliverable guard-stop notices accumulate in the policy outbox and its notifier re-reminds them every few hours; once their content is genuinely consumed (it persists in the internal journal), the sanctioned cleanup is the policy CLI's `fail-notifications --all-pending` — never a direct outbox/DB edit; the CLI's read-only `status` gives pending approvals/notifications counts before and after (a drained outbox also proves the delivery channel revived, e.g. after a gateway restart). Still forbidden: opening a PTY to fake the owner TTY on the CLI path, forging author identity, and auto-deciding any serious category. When one approval class chronically fires on safe worker actions (recurring stale bindings for scratch/temp cleanup), the owner's durable fix is WEAKENING the policy rule itself — a scoped safe-path exemption shipped as a reviewed code change («вместо автовыдачи лучше ослабить правильно политику») — not runtime auto-approval logic.
- Do not send a real Telegram canary by default. Validate with fixtures, parser tests, configuration readback, and isolated state. A real canary requires explicit scope and must be removed with delivery readback afterward.
- Do not run watchdogs against live state for preview. Use copied scripts, isolated state paths, and fixture-fed command results.
- Do not edit live cron storage directly. Use the supported cron interface, preserve a backup, and read back every field that matters. Pitfall: `hermes cron edit <id> --model/--prompt/--pin ...` silently rewrites the job's `deliver` back to the owner DM — after ANY CLI cron edit, read the job back via cronjob_manage list (the raw jobs.json parse can omit fields like `pinned` that the tool shows) and re-set `deliver` to the canonical route (the «Вести» thread of «𝗕 🌐 и CX» — current thread_id per `references/cx-group-routing.md`; the id CHANGES when the topic is recreated, never trust a memorized value); verify model/provider/pinned/continuity in the same readback.
- Never inspect board storage directly. Use supported Kanban tools or bounded CLI output where policy permits. Raw inline sqlite through terminal is doubly bad: policy classifies the command ARGUMENT TEXT lexically, so a read-only `mode=ro` query whose inline text mentions policy-plane words (rule ids, state-db paths, even inside comments) is denied as `policy_control_plane_mutation` — a false positive you cannot argue away. Compliant routes: native Kanban tools and permitted bounded CLI list/show output. No real board/control-plane SQLite access, including read-only queries packaged in a script; a missing native read/edit primitive is a capability prerequisite, never an opaque-script exemption.
- Long-running kanban coordination: a steer comment reaches a RUNNING worker at its next tool boundary, but a respawned run starts without prior context — put the full delivered state (candidate location, test commands, expected results, what NOT to redo) into a workspace HANDOFF file, not only into card comments. Before handing a self-authored candidate to independent QA, run an adversarial stress test (multi-tick drain, mixed edge-case inputs): narrow happy-path suites pass while adversarial mixes expose permanent stalls, and catching that pre-review saves a QA round-trip. Lifecycle transitions (`request_review`, `complete`) refuse while another run holds a live claim — `kanban reclaim` first (it also stops the stale worker), then transition; if your session already produced the deliverable, reclaim and post ONE steer comment naming artifact paths so the spawned worker verifies instead of rebuilding. When a review card blocks AFTER the reviewer already posted a verdict (e.g. policy false-positive on cleanup commands), read the comments first and unblock to let the recorded verdict finalize — never dispatch a fresh QA run over work that has an independent PASS.
- When a route/canon value you just set comes back reverted, or a memory/skill replace fails with «no entry matched»: suspect a CONCURRENT session carrying a newer owner directive before retrying — use session_search or an approved native redacted metadata export for the exact affected surface; no direct state.db reads. Two writers re-asserting their own value thrash shared state (jobs.json, webhook routes, memory); the newest owner directive wins, converge on it and record the superseded value as historical, never re-apply yours over it. Two consecutive `no entry matched` memory-replace failures are a hard stop, not an invitation to vary the substring: the live store already diverged from the context-injected copy, so no old_text drawn from context will match — re-read live state and adopt it.
- Before editing any shared route state (cron deliver, webhook subscriptions, BOARD_TOPIC), re-read it fresh at edit time: the board_topic_router guard rewrites kanban subscriptions every 5 minutes to match BOARD_TOPIC, so a manual notify-subscribe without a BOARD_TOPIC update is reverted within one guard pass.

## Audit flow

1. Enumerate delivery surfaces: cron routes, gateway lifecycle notifications, Kanban subscriptions, and webhook routes.
2. Classify each as decision, material information, critical incident, duplicate board state, self-healing transient, or stale history.
3. Fix the source of repeated alerts before changing reminder cadence.
4. Preserve genuine owner decisions; suppress only duplicates and stale artifacts.
5. Verify configuration and state read-only. Test formatting against fixtures; use a real authorized canary only when delivery itself is the acceptance criterion.

## Polling-watcher triage (transient source failures)

A watcher alert ≠ broken source. Before touching the endpoint, deployment, or cron job:

1. Reproduce the watcher's EXACT request (same URL, token, cursor/query params) with a live HTTP probe. A healthy 200 + valid payload proves the source is fine and the alerts were transient blips — never redeploy on blip evidence alone.
2. Read failure shape from cron output logs (`profiles/<p>/cron/output/<job_id>/`, grep the alert text for timestamps): scattered failures between silent OK ticks = transient flakiness (common on Google Apps Script anonymous `/exec` redirect endpoints — self-heals in a tick or two); failures on EVERY consecutive tick = genuinely broken endpoint/deployment.
3. Check data-loss exposure: if the watcher only advances its cursor on success, transient failures lose nothing — say so explicitly to the owner.
4. Fix the noise at the watcher: retry 404/5xx inside the tick (2 attempts, ~10s pause), alert only on the first tick of a streak (streak counter in the state file), stay silent on recovery, cap reminders at one per several hours during a long streak. A watcher that shouts on every failed tick spams the owner with self-healing events. Deduplicate per alert CLASS with a cooldown map in the state file, never by whole-message signature: a signature built from acted/class counts changes whenever the class set changes, so already-reported classes re-notify on every tick (observed: the majority of a day's owner messages were one watcher re-announcing the same deny classes).

Watcher scripts live in `profiles/<profile>/scripts/` with config/state JSON beside them — not in cron dirs; the cron job only references the script name.

## Cron delivery_failed audit («джоб отработал, но результат не дошёл»)

`hermes cron list` distinguishes `ok` / `ran, but the result was not delivered (delivery error: …)` / `error: …`. Treat `delivery_failed` as DATA LOSS, not a failed job: the artifact exists in `profiles/<p>/cron/output/<job_id>/` — recover and re-deliver it before/while fixing the route. Recurring root causes:

1. **Interpreter split**: `python-telegram-bot not installed` while the gateway venv demonstrably has it — the delivery path ran under a different interpreter (`.hermes-runtime` generation copy / system python). Check the failing path's interpreter first; installing into the wrong venv changes nothing.
2. **Corrupted target**: malformed chat_id (e.g. a `-100` supergroup prefix glued onto a plain user_id) yields `Chat not found` — diff the stored deliver target against the canonical route map char by char.
3. **Stale pre-migration targets**: jobs still pointed at an old DM/thread after a route migration — sweep ALL surfaces, not just the reported job: `deliver` AND `failure_deliver` in every profile's cron store, `webhook_subscriptions.json` (`deliver_extra.thread_id`), hardcoded `hermes send -t` targets in `profiles/*/scripts/`, `board_topic_router.py` BOARD_TOPIC, kanban notify-subs, and the skill/memory canon. Grep the old `chat:thread` string across `profiles/*/` (excluding `*.bak*`/backups) to prove zero leftovers. A dead thread_id does NOT produce delivery errors — send returns `sent` and the message lands in the group's General topic, so silence in the intended thread is the only symptom.
4. **Model-side death**: `N failures in a row` with 402/429 quota text is not a delivery problem at all — the job never produced output; route to pool/quota repair.

## Escalation-delivery audit (owner: «почему результат/блок не дошёл до меня?»)

Answer with evidence from the delivery chain — never speculate:

0. If NOTHING arrives at all (not one item, owner's own DMs to the bot get no reply), check the platform adapter layer before any watcher: `gateway_state.json` per-profile `<profile>:telegram` entries for `fatal`/`duplicate_credential` parking and gateway.log `Blocked unauthorized user <owner_id>` lines — a parked adapter rejects even the owner at intake, so nothing downstream can deliver. Full triage → skill `hermes-botfleet-health`, `references/gateway-platform-state-triage.md`.

1. Watcher state file (`profiles/<p>/scripts/<watcher>.state.json`): is the card in `seen` at all, with which `esc_level` and `first_seen`/`last_reminded`? A company-level item is silent BY DESIGN (owner sees only owner-boundary items + >2h/>4h escalations); say so instead of hunting a bug.
2. Cron output dir (`profiles/<p>/cron/output/<job_id>/*.md`): grep it for the card id. Silent ticks are stored as `Status: silent (empty output)`; a message that was PRODUCED has a timestamped .md. No .md containing the id = the watcher never emitted it.
3. Gateway log: `Sending response (N chars) to <chat>` / `Flushing text batch` lines prove actual Telegram delivery — cron `last run ok` means the script exited 0, NOT that anything was sent. Kanban notify/wake firings appear as `kanban notifier: woke agent for <task_id>` lines — a completed card with a valid notify-subscription and NO such line is a notifier-path defect (deliver the result manually and card the defect), not worker silence.
4. If the outbox drains with `sent: 0` while pending rows exist and their bound tasks are LIVE: suspect the delivery turn itself. The projector delivers via `hermes chat -c "Bot Chat" --create-if-missing -Q`; a HEAVY resumed Bot Chat session (700+ messages) can hang past the 90s delivery timeout forever (rows released back to pending each tick = eternal loop) and may restore an exhausted pinned model from session metadata. Fix: archive/delete the heavy session (`hermes sessions archive --older-than 1d --min-messages 700`, then `sessions delete <id> --yes`) so the next drain creates a fresh one, and keep the delivery-model pin env (`FP_DELIVERY_MODEL`/`FP_DELIVERY_PROVIDER`, set by fleet_policy_notify.py to a cheap live rail) so delivery never depends on session-restored model state.
5. Night-deferred lines: the quiet-hours buffer lives ONLY in the state file and is overwritten wholesale each tick, cleared on the post-08:00 flush — a gateway restart in the deferral window silently drops it. Durable fix = append-only deferred journal + a re-surfacing rule (owner-level item never confirmed delivered keeps re-appearing); until that ships, after any overnight gateway restart diff `seen` owner-level entries against the cron outputs and hand-deliver the gap.

## Token economy of TG delivery (owner 29.09 «оптимизировать расход токенов при общении через тг канал и топики»)

- Measured 29.09: prompt-cache hit ≈96% (healthy — do NOT chase cache); the real cost drivers are (a) IMMORTAL topic sessions — every owner message/notify-wake re-sends the whole tail (topics 129/20 reached 12.7k/11.7k messages; top-12 TG sessions burned 51M input + 1.16B cache-read cumulative), and (b) `notify+wake` kanban subscriptions — every card event spawns a full agent turn on the topic session.

- Session hygiene (native, 29.09): plugin `hermes-session-reset-policy` v0.3.0 (fastfinge, commit a91a4cc, profiles/company/plugins/, hot-reloads on `plugins enable`) re-arms timed resets the core retired: `session_reset.mode: both`, `idle_minutes: 480`, `at_hour: 4` — first inbound message past the boundary starts a FRESH session via the gateway /new funnel (transcripts/state.db consistent, no timers). - ENV-PIN pitfall (29.09 incident, full diagnosis: `ventures/docs/fleet-ops/KANBAN_TENANT_DIAG_2909.md`): the dispatcher injects `HERMES_KANBAN_DB/BOARD/WORKSPACES_ROOT` into worker envs and env BEATS the `--board` flag (official since ≥25.09).
