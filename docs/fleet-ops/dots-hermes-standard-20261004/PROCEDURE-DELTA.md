Scope — только procedural memory активного company-профиля; не установка адаптера и не разрешение менять другие профили. Эта запись перечисляет реально выполненные skill_manage edits, а не независимый QA PASS. Subject/candidate/baseline snapshots остаются неизменными.

## Закреплённое правило

1. Внешнюю механику сравнивать ДО раскатки: внешний source/locus, официальная Hermes-механика, installed/source evidence, действующий владелец, конфликт/дубль/предел, reuse/reject/clarify. Общие процессы указывать ссылкой на прежнего владельца; не копировать вторую schema, очередь, координатора, approval flow, storage или обязательный шаблон ответственности.
2. Новая reference + небольшой hook — scoped additive update; замена прежней reference — сохранить её entrypoint и заменить единственный точный старый suffix на новый. Сравнивать собственный before-minus-old-hook с after-minus-new-hook.
3. Whole-skill sync допустим ТОЛЬКО при отдельно разрешённом whole-skill scope. Старое общее «после любой правки найти и синхронизировать все копии» сужено до разрешённого режима/allowlist; разные root-хэши при scoped update не дефект.
4. Перед atomic replace повторно сверять current bytes; новый foreign diff → сохранить target, HOLD. Собственные root revisions и остальные Markdown-файлы сохраняются. Откат — только собственные after-hash к подтверждённым before bytes, не восстановление чужого нового root.
5. Counts брать из фактических receipt dictionaries и hash manifests, не из текстового PASS. Разделять source acceptance, установку, native registration, natural load, live behavior, platform delivery и финансовый эффект.
