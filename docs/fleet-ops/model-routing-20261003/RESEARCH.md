## 1. Паттерны (10)

### 1.1. RouteLLM — обученный бинарный классификатор «сильный/слабый»

LMSYS/UC Berkeley обучают роутер на preference-данных Chatbot Arena: классификатор решает, достаточно ли слабой (дешёвой) модели для запроса, или нужна сильная. На MT Bench — снижение стоимости более чем на 85% при сохранении 95% качества GPT-4; на MMLU — 45%, на GSM8K — 35% экономии при той же планке качества. Роутеры генерализуются на пары моделей, не входившие в обучение. Для нас релевантен как доказательство верхней границы выгоды от бинарного «дёшево/дорого» решения, принятого ДО инференса.
URL: https://www.lmsys.org/blog/2024-07-01-routellm (2024-07-01); https://arxiv.org/html/2406.18665v4; https://github.com/lm-sys/routellm
Confidence: высокий (peer-reviewed arXiv + код).

### 1.2. FrugalGPT — каскад с обученным скорером останова

Stanford (Chen, Zaharia, Zou) предлагают LLM cascade: запрос идёт по цепочке моделей от дешёвой к дорогой, обученный скорер решает, достаточно ли хорош ответ, чтобы остановиться. На датасете HEADLINES FrugalGPT совпал с качеством GPT-4 при снижении стоимости до 98%, либо превзошёл GPT-4 на 4% при той же стоимости. Цены API в обзоре различаются до двух порядков между моделями — это и есть фундамент выгоды каскада.
URL: https://arxiv.org/abs/2305.05176
Confidence: высокий (arXiv, Stanford).

### 1.3. Лестница стратегий роутинга и «routing ≠ failover»

TrueFoundry описывает лестницу рунгов возрастающей сложности: статические правила → взвешенные сплиты → latency-aware → cost-aware → семантический роутинг → каскады. Ключевой тезис: каждый ранг должен оправдываться измеренной пользой, а не модой; роутинг (оптимизация) — это не failover (доступность), хотя они делят механику кандидат-листа. Иллюстративный инцидент: инженер получил 41% снижения счёта за квартал простым классификатором, но на вторую неделю счёт вырос втрое из-за дрейфа верификатора каскада, который молча эскалировал всё подряд.
URL: https://www.truefoundry.com/blog/llm-routing-cost-quality-aware-model-selection (2026-06-08)
Confidence: высокий (вендорский инженерный блог, число 41% — иллюстративный кейс, не бенчмарк).

### 1.4. Каскады с confidence-эскалацией и живой стоимостью эскалации

Tian Pan разделяет routing (одно решение до исполнения) и cascading (последовательная эскалация от дешёвого к дорогому по порогу уверенности). Приводит экономику: frontier-модель класса Claude Opus ≈ $5/$25 за млн input/output токенов против $1/$5 у эффективной модели того же семейства — спред 5×; с роутингом 85% запросов на дешёвый тир дают 45–85% снижения стоимости при 95% качества. Подчёркивает: эскалационная ставка (escalation rate) — живая стоимостная переменная, а не константа проектирования.
URL: https://tianpan.co/blog/2025/11/03/llm-routing-model-cascades (2025-11-03)
Confidence: средне-высокий (практикующий инженер, цены указаны «roughly»).

### 1.5. Overhead роутера: правила <1 мс, embedding 5–20 мс

Сравнение RouteLLM и vLLM Semantic Router (Ginger Labs) фиксирует порядок величин латентности решения: rules-based роутинг < 1 мс, embedding/ML-роутинг 5–20 мс — на фоне 500–2000 мс самого инференса. Вывод для флота: детерминированный роутер на правилах (наш ROUTES-список) добавляет пренебрежимую задержку; семантический слой имеет смысл только когда caller не может дёшево пометить задачу сам.
URL: https://gingerlabs.ai/blog/routellm-vs-vllm-semantic-router (2026-06-20); подтверждение диапазона: https://www.truefoundry.com/blog/llm-routing-cost-quality-aware-model-selection
Confidence: средний (технический блог; порядок величин сходится между источниками).

### 1.6. Semantic/signal-driven роутинг (vLLM Semantic Router)

Проект vLLM Semantic Router (Red Hat/vLLM, Apache 2.0, ~5.3k звёзд на дату сбора) — программируемый слой Mixture-of-Models: маршрутизация по сигналам запроса, предпочтениям и политикам. По данным сравнительного обзора, на MMLU-Pro их signal-driven подход даёт +10.2% accuracy, −47.1% latency, −48.5% token usage против бейзлайнов. Для нас это верхний ранг лестницы: имеет смысл только при неоднородных неклассифицируемых запросах; у нас dispatcher сам маркирует task_type.
URL: https://github.com/vllm-project/semantic-router; числа: https://gingerlabs.ai/blog/routellm-vs-vllm-semantic-router
Confidence: средний (метрики из вторичного обзора, не из пейпера напрямую).

### 1.7. Community-signal роутинг (OpenRouter Auto Beta)

OpenRouter Auto Beta классифицирует запрос в ~30 типов задач (code:debugging, agent:multi_step_planning, research_report и т.д.) и ранжирует модели по реальной доле расходов сообщества на этом типе задач за скользящее 7-дневное окно — живой сигнал без переобучения. Пользовательский дайл cost_quality_tradeoff (cqt) фильтрует пул по цене; при недоступности классификатора роутер деградирует к дефолтному набору, а не падает. На GPQA Diamond качественный конец (cqt=0) дал 83.8%.
URL: https://openrouter.ai/docs/features/model-routing
Confidence: высокий (первичная документация провайдера).

### 1.8. Per-task model routing + prompt caching как главный рычаг (Claude Code playbook)

Traversaal-разбор экономики Claude Code: маршрутизация простых подзадач на Haiku вместо Sonnet/Opus снижает стоимость задачи в 10–20× без потери качества; кэш-хиты тарифицируются примерно в 10% от стандартной input-цены (до 90% скидки на кэшированный префикс у Anthropic, ~50% у OpenAI). Критично для нас: авто-компакция и переупорядочивание стабильного префикса ломают кэш — то есть переключение модели посреди живой сессии обнуляет накопленный кэш. Комбинация кэширования, роутинга и гигиены контекста даёт суммарно 50–80% снижения токен-спенда.
URL: https://blog.traversaal.ai/claude-code-cost-optimization-benchmark-playbook/ (2026-07-24); https://managed-code.com/blog-post/prompt-caching-explained (2026-07-03); https://openai.com/index/api-prompt-caching/ (авто-кэш от 1024 токенов)
Confidence: средне-высокий (прайсинг-проценты подтверждаются первичными доками OpenAI/Anthropic).

### 1.9. Измерение качества роутинга: evals, LLM-as-judge, A/B против бизнес-метрик

Роутинг «на качество» требует измеримого определения качества: оффлайн eval-сеты, онлайн LLM-as-judge или A/B против бизнес-метрик; «роутинг на вайбах» — способ отгрузить регрессию незамеченной (TrueFoundry). DigitalOcean фиксирует лучшие практики LLM-as-judge: явные рубрики, репрезентативные датасеты, периодическая валидация против человеческой разметки; для задач с единственно верным ответом (классификация) достаточно простых метрик. Для флота это опора нашей фазы C (shadow) и метрики QA-block rate по классам.
URL: https://www.truefoundry.com/blog/llm-routing-cost-quality-aware-model-selection; https://www.digitalocean.com/resources/articles/llm-as-a-judge (2026-08-14)
Confidence: высокий (два независимых источника сходятся).

### 1.10. Раскатка роутинга: shadow → mirror → canary → full (фича-флаг малой долей)

Future AGI разводит четыре паттерна: shadow (кандидат не виден пользователю, полное дублирование трафика, стоимость 1×), mirror (семплированное зеркало, стоимость N%), canary (живая стратифицированная доля с rollback, стоимость = размеру среза), race (параллельный фан-аут под latency SLO, стоимость N×). Рекомендуемая воронка промоушна: shadow → mirror → canary → full. Классический инцидент: миграция на новую модель с включением 100% трафика сразу — минус 9 пунктов function-call accuracy и плюс 7 пунктов refusal rate к полудню. Прямой аналог нашей фазы C (shadow-лог без принуждения) перед фазой D (пины).
URL: https://futureagi.com/blog/llm-eval-shadow-traffic-canary-2026/ (2026-05-21)
Confidence: средне-высокий (вендорский блог, но паттерны стандартны для индустрии).

## 2. «Не применять у нас» (4)

### 2.1. Пер-сообщенческое переключение модели внутри живой сессии
Причина: ломает prompt cache. Кэш работает по стабильному префиксу у одной модели; смена модели или переупорядочивание контекста обнуляет кэш-хиты, которые сами по себе дают до 90% скидки на повторный префикс (Anthropic; ~50% у OpenAI). Совпадает с инвариантом №5 программы (внутри живой сессии модель не переключаем). Источник: https://blog.traversaal.ai/claude-code-cost-optimization-benchmark-playbook/, https://managed-code.com/blog-post/prompt-caching-explained.

### 2.2. Embedding/семантический роутер как первый ранг
Причина: 5–20 мс дополнительной латентности и обучение/калибровка классификатора не окупаются, когда caller (диспетчер канбана) уже дёшево маркирует задачу точным task_type. TrueFoundry прямо: семантика бьёт статический тег только когда caller не может пометить запрос сам. У нас класс известен до старта (7 классов ROUTES). Источник: https://www.truefoundry.com/blog/llm-routing-cost-quality-aware-model-selection, https://gingerlabs.ai/blog/routellm-vs-vllm-semantic-router.

### 2.3. Тихий fallback (молчаливая подмена модели на ходу)
Причина: запрещён владельцем и инвариантом №1 (выбор только ДО старта; тихой подмены нет). Индустриальное подтверждение риска: conflation роутинга и failover — причина инцидентов; fallback-цепочки должны быть отдельным механизмом с логом и причиной, как в программе («шаг вправо по списку — явный пер-картовый пин, с логом»). Источник: https://www.truefoundry.com/blog/llm-routing-cost-quality-aware-model-selection, https://docs.litellm.ai/docs/proxy/reliability.

### 2.4. Обученный ML-роутер (RouteLLM-style matrix factorization) на текущем масштабе
Причина: требует preference-датасета и калибровки порога (RouteLLM калибрует threshold под целевую долю вызовов сильной модели, напр. 50% → threshold 0.11593); при 2-модельных упорядоченных списках на класс и детерминированных жёстких правилах флота обученный роутер — неоправданная сложность (верхний ранг лестницы без измеренного дефицита простых правил). Источник: https://github.com/lm-sys/routellm (quickstart с calibrate_threshold), https://www.truefoundry.com/blog/llm-routing-cost-quality-aware-model-selection.
