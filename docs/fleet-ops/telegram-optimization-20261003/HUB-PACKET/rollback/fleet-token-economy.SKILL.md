# Fleet Token Economy

Class: diagnose where fleet tokens go and cut consumption without breaking quality gates. Owner prioritizes token economy. Measure first, propose levers with evidence, apply only approved ones, verify after.

## Measure first (never guess)

1. `hermes insights --days N` — raw input/output tokens, model/platform/tool/skill breakdowns. Note: "Total tokens" includes context re-transmission/cache and is far larger than raw input+output. Most fleet traffic is usually `subscription_included` (quota/latency, not invoice) — frame savings accordingly.
2. `hermes prompt-size --json` — fixed per-prompt budget: system prompt, skills index, memory, user profile, tool schemas. Every disabled skill shrinks EVERY future prompt.
3. Per-profile `state.db` (read-only `file:...?mode=ro` URI): `sessions`, `messages.tool_calls`, `session_model_usage` (input/output/cache_read per model+billing_mode). Recipes + tested SQL in `references/audit-recipes.md`. PITFALL daily-срезов: строки `session_model_usage` накопительные по (session, model, task), а не дневные — фильтр `last_seen >= day_start` даёт точные ВЫЗОВЫ за день, но токены carryover-сессий (first_seen < сегодня) включают прошлые дни; в отчёте разделяй new/carry и помечай токены как накопительные. Здоровье провайдеров за день — из логов: `grep '<дата>' profiles/*/logs/agent.log | grep 'API call failed'` с разбором `model=`/`error_type=`, а не из БД.
4. `hermes cron list` — check `deliver` targets and `last_delivery_error`; cron deliveries can run full agent turns. Classify by mode: `Mode: no-agent` script jobs cost zero tokens; agent-mode jobs run a FULL agent turn per fire — convert deterministic high-frequency agent jobs to no-agent scripts.
5. **Wasted-turn audit** — two state.db scans insights cannot show: repeat loops (same tool + same normalized args ≥6× inside one session) and error turns (tool results carrying error payloads, classified by distinct pattern per profile). Every loop iteration and error retry re-transmits the whole context. Recipes in `references/audit-recipes.md`.

## Levers (typical impact order)

1. **Session hygiene** — biggest free lever. Long-lived sessions re-transmit context every turn; a 17–20k-message session is a per-turn tax. `/new` after big tasks; `hermes sessions archive/delete/prune` for dead ones. PITFALL: legacy `session_reset.*` config keys (mode/idle_minutes/at_hour) are IGNORED by the current kernel — gateway sessions end only on explicit `/new`/`/reset`, compression stays automatic. Never promise timer-based auto-reset because a config block exists: verify a config key is actually read by the installed kernel (grep it in config_defaults.py / runtime) before advising the owner. Background fleet work is unaffected either way — every cron fire and kanban dispatch starts a fresh session; `/new` hygiene matters only for interactive chats.
2. **MoA fan-out** — with MoA enabled each user turn pays reference models + aggregator. Real switch is preset-level: `hermes config set moa.presets.default.enabled false` (see pitfalls).
3. **Compression** — `hermes config set compression.protect_last_n / target_ratio / protect_first_n`.
4. **Reasoning effort — ЗАПРЕЩЁННЫЙ рычаг на DashScope-профилях.** Директива владельца (20.09, подтверждена жёстко 22.09): все DashScope-модели (qwen3.8-max, kimi-k3) во всех слотах (main, delegation, ВСЕ auxiliary) = reasoning **max**, «можно не экономить». Никаких max→high/low даунгрейдов на DashScope, включая тривиальные aux (title_generation, memory_query_rewrite и т.п.) — даже когда замеры показывают перерасход. Перед любым предложением по effort — сверить fleet-doctrine «Aux offloads paid rails». Effort-правки допустимы только на GPT-профилях и только с явного одобрения владельца.
5. **Skills index** — disable never-loaded skills via `skills.disabled` in config.yaml (reversible, files untouched). Stronger variant when hundreds of zero-use skills sit on disk: physical quarantine (reversible mv + `.no-bundled-skills` marker so updates don't re-seed bundled copies) — full procedure and pitfalls in skill `fleet-skills-rollout` §«Карантин zero-use скиллов по флоту». Estimate ≈ name + min(desc,140) chars per skill per fresh prompt. Measured (02.09): 64 disables → skills index 16,421→11,078 chars (−33%, ≈1.3k tokens per fresh prompt); verify with `hermes prompt-size --json` before/after. Note: skills disabled in ONE profile's config only shrink that profile's prompts; each profile loads its own skills tree.
6. **Cron delivery targets** — `bot-chat:<profile>` resumes that profile's Bot Chat session and runs a FULL agent turn every fire; drop it when the real channel is Telegram, and keep bot-chat sessions short.

## Mechanics & pitfalls

- **Config writes:** `patch`/`write_file` on a profile config.yaml is refused by the agent guard — always use `hermes config set key value` via terminal. Take a timestamped backup copy first; verify each value with `hermes config get`.
- **Unknown-key warning matters:** if `hermes config set` says a key is "not recognized", the intended consumer may not read that path. Verify in hermes-agent source before claiming the change works. Example: flat `moa.enabled`/`moa.fanout` are ignored when a `moa.presets` block exists — the loop reads preset-level `enabled` (agent/moa_loop.py: disabled preset ⇒ empty reference fan-out, aggregator acts alone).
- **Probe-verified wire flags are exactly as broad as the probe:** per-profile flags like `model.reasoning_echo` apply to the profile's CURRENT provider — enabling fleet-wide off one provider's probe risks 400/422 on strict providers that reject echoed fields, and «accept+ignore» providers gain pure token weight with zero benefit. Enable only where a live probe proved accept AND honour. DashScope facts (probed): qwen3.8-max honours reasoning_content echo; kimi-k3 ignores it; zai/glm and openai-codex unverified → keep off. Details in `references/harness-efficiency.md`.
- **Kernel releases silently re-inflate the static footprint** (observed: tools 41→52, system prompt ~2× after a release lane) — re-run `hermes prompt-size --json` after every release before claiming trim/deferral levers are still applied.
- **fleet-policy:** direct sqlite reads of kanban.db and the sessions dir are blocked — use `kanban_*` tools and `hermes sessions ...` CLI. Read-only `mode=ro` queries on `state.db` pass.
- **`hermes skills list` truncates names** to ~20 chars with `…` — never join audit data against that output. Walk skill dirs on disk and read frontmatter `name:`/`description:`; when matching the installed set, treat `…` as a prefix match.
- **Skill usage audit:** count actual `skill_view` calls in `messages.tool_calls` over N days across ALL profiles (script: `scripts/skill_usage_audit.py`), normalize `category/name` and `category:name` forms to the base name, and cross-check disk frontmatter names (folder renames happen).
- **Duplicate skill copies across dirs** (global `~/.hermes/skills` + per-profile `profiles/<p>/skills`): they do NOT stack token cost within one prompt (each profile loads only its own tree) — so disabling via config is sufficient for tokens; deleting duplicate files saves disk only. Compare by SHA-256 of SKILL.md before touching anything; several identical pairs exist with byte-different variants (company-side usually the edited one).
- **Tiering the disable list:** safe = legacy of deleted projects + never-loaded heavy packs (creative/productivity/rampstack); hold back = recently installed packs the owner chose + "dormant insurance" skills likely needed soon (pdf, xlsx, google-workspace). Present tiers and get explicit approval per tier before disabling.
- `hermes config set skills.disabled '[...]' --force` — the flag only suppresses the unknown-key notice; `skills.disabled` IS a read key (consumed by skill_utils), so the list works despite the warning.
- **Skill body size is a per-load cost** — every `skill_view` injects the full SKILL.md into context. Keep only always-on rules in SKILL.md and move depth into on-demand `references/`; when auditing tokens, inspect the largest SKILL.md files in the profile (one slimming pass can cut ~80% of chars without dropping any rule). Rank skills by weekly injection = loads × chars/4, not by load count alone — one 150KB SKILL.md loaded 160×/week is ~6M injected tokens before re-sends; split top products into a ≤3.5KB always-on core + references/.
- **Skill reload loop after compression:** context compression prunes loaded skill bodies (`[SKILL_PRUNED]` markers) and the agent re-loads them via `skill_view` — in long sessions this reaches hundreds of loads of one skill. Detect via same-args `skill_view` counts per session (≥6 suspicious, ≥50 a loop) — but FIRST dedupe tool_calls rows by call_id: state.db stores duplicate rows for identical calls and inflates raw same-args counts up to ~9×, so a moderate reload pattern can look like a loop and a «419×» claim can be a 68-unique-call artifact. insights "Top Skills" loads hide this because they aggregate across sessions. Cure = slim SKILL.md bodies + short-lived sessions, never more reloading.
- **Error turns are a token multiplier:** every failed tool call costs a full context re-send on retry. Classify tool-result errors by distinct pattern per profile (policy blocks incl. false-positive guard hits on safe commands, schema misuse like missing completion summary, wrong flag types, missing task_type markers, same_failure_loop, timeouts) and fix the top patterns — a 10% error rate on 150k weekly tool results is ~15k wasted turns.
- **CLI run pitfalls:** `hermes insights` can take minutes on a large state DB — redirect to a file with a 600s timeout, don't pipe through head at default timeout. Never share scratch files via `/tmp` between terminal (MSYS) and execute_code (Windows python) — resolve an absolute Windows scratch path in the same call, or rerun the CLI inside a python subprocess (shell=True) and parse stdout in one call. Filter `Config ref ...` warning lines before parsing. Parse box-table output (cron list) with a stateful python line parser; grep/paste column joins break on box-drawing chars.
- **Verify after changes:** config applies to NEW sessions only; re-run `hermes insights` after 2–3 days to confirm the delta. Gateway restart is not required but kills live sessions — ask first.
- **Test-fires can fail for unrelated reasons:** a manual cron test-run failed on provider HTTP 429 (rate limit), not config — don't read a failed test-fire as proof a change broke; judge config by readback + the next scheduled run.
- **Desktop GUI automation is a context bomb:** `computer_use`/accessibility-tree inspection returns thousands of nodes into the conversation — one dump of a settings/board window can exceed an entire task's budget, and the owner treats it as «тратит токены в пустоту» whenever the same action had a native tool or CLI path. Route lifecycle/board/config actions through `kanban_*` tools and CLI first; use GUI automation only for genuinely visual work, and never to hunt for a button.
- `rtk init -g --agent hermes` (rtk CLI present on this host) advertises automatic command-output token savings; unverified in this fleet — evaluate before enabling, don't promise it.

## Routing-audit safeguards

- Inspect the current named-provider catalog as well as primary/fallback slots. New relays may exist only in `company`, while Groq/Mistral/Cloudflare exist only in `default`; profile configurations are independent. Export only allowlisted routing metadata, never whole configs or credential stores. Group/deduplicate the export before printing it to avoid flooding the audit context.
- Separate configured reasoning from effective reasoning. Current Hermes documentation says title generation disables thinking at the call site, overriding its auxiliary effort; same-model background review inherits the parent effort for cache parity, ignoring its own auxiliary effort. Do not claim a `max` title setting caused reasoning spend or promise that lowering same-model review effort will save tokens without checking the installed call path.
- Report provider-list entries as configured credentials, not validated availability. A local `429 (ready to retry)` is historical cooldown metadata, not proof of a current outage or recovery. Relay public prices are estimates subject to account/group multipliers; `cost_status=unknown` with zero cost fields means unknown, not free — and `cost_status=included` with 0 USD means subscription-included: quota/latency burn is real, so report it as quota consumption, never as free/zero. `reasoning_tokens` may already be counted inside `output_tokens` in the installed accounting — list them side by side, do not sum them.
- Preserve usage scopes: group auxiliary calls by the `task` column and leave empty task labels unattributed; model usage alone does not identify delegation or prove accepted-output quality. Keep cached input and reasoning separate unless the installed accounting semantics justify a sum.
- On Windows Git Bash, if `hermes` is not on PATH, discover its `.cmd` wrapper with `where.exe hermes`, read that wrapper, then use its absolute venv executable. Do not retry the unresolved shell command or install another Hermes copy.

## From audit to program

Freeze a baseline (total tokens, error rate, top repeat loops, largest sessions) in a plan file with per-lever targets and kill criteria; make each lever an independent, revertible kanban card with its own reviewer. The baseline MUST include a boundary snapshot of the cumulative per-profile counters (session_model_usage sums) at the window edge, taken BEFORE the levers deploy — counters are cumulative and messages.token_count is unfilled, so without the boundary snapshot the savings % is unmeasurable after the fact and the control reports null. Verify each lever is actually LOADED per profile (file-size/hash readback of the touched skill/config), never from the rollout card's report alone — «фактически загружено ≠ заявлено»; schedule a weekly no-agent delta-audit cron that recomputes the exact same metric definitions and reports the delta to the baseline. Money saved stays `null` when sessions lack pricing data — report tokens, not currency. When the owner compresses the program window (e.g. two weeks → 48h): update every lever card's deadline AND re-issue the directive as card comments (ready cards are claimed within ~1 minute, so body edits after dispatch never reach the running worker), rescale the baseline proportionally for the control measurement (48h window ↔ per-48h slice of the 7-day baseline), schedule a one-shot control cron at the window end, and pre-declare which levers physically cannot deploy in time — report them «partial» at control time, never tune numbers to hit the target.

## Prompt-audit лейн (канон 25.09, адаптация Anthropic /claude-api prompt-audit)

Подход Anthropic: аудит промптов/скиллов/памяти против ТЕКУЩЕЙ модели. Два вида устаревшего текста: (1) «буквальные» инструкции («проверь дважды», «будь максимально тщателен», самодельный scratchpad, жёсткие N-шаговые скрипты) — жгут токены (до −⅓ стоимости задачи при удалении); (2) текст под мёртвые модели/профили/противоречивые правила — жжёт точность (−7…11 пп). Замеры Anthropic: устаревший промпт = +36% стоимости; после аудита −14% стоимости и точность 92→97%. Команду `/claude-api prompt-audit` НЕ переносить — это Claude-Code-специфика; у нас свой детектор.

Наша реализация: `profiles/company/scripts/prompt_audit.py` — no-agent cron `d341b0d4a136` daily-prompt-audit (ЕЖЕДНЕВНО 08:15; до 30.09 был еженедельным), доставляет в тред 281, молчит при неизменённом hash находок (`prompt_audit.state.json` — watermark как у deny_triage/cap_tool_watch). Рубрики находок (объективные, малошумные): P1 мёртвая маршрутизация (@rr-*, rr-critic/ops/pool/mkt-lead/mkt-smm/support/frontend/backend), P2 мёртвые пины моделей (ox-alpha/stealth/ox, gpt-5.6-luna, gpt-account-2/terra), P3 «проверь дважды»-антипаттерны (verify twice / double-check your work / scratchpad / step by step), P5 MEMORY>7400 / USER>2350 / SOUL>9000 (warning-полоса перед жёсткими потолками 8000/2500). INFO-строка вне hash: число desc>60. Исключения (false-positive guard): строки-надгробия («удалены/removed» — историческая справка о миграции, НЕ маршрутизация), author/created_by/owner-поля frontmatter скиллов, rr-team (живая доска), rr-project/rr-landing (живые скиллы), rr-* worktree-папки и repo-индексы.
