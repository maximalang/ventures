# fleet-token-economy — mechanics & pitfalls

> Topic-focused reference — moved from this skill's SKILL.md by hub compaction (t_cef261ac, 2026-10-03, SOURCE-ONLY packet). Original text preserved verbatim; inline `(UPDATE 2026-10-03 ...)` marks are documented corrections recorded in INVARIANT-MAP.json.

## Mechanics & pitfalls

- **Config writes:** `patch`/`write_file` on a profile config.yaml is refused by the agent guard — always use `hermes config set key value` via terminal. Take a timestamped backup copy first; verify each value with `hermes config get`.
- **Unknown-key warning matters:** if `hermes config set` says a key is "not recognized", the intended consumer may not read that path. Verify in hermes-agent source before claiming the change works. Example: flat `moa.enabled`/`moa.fanout` are ignored when a `moa.presets` block exists — the loop reads preset-level `enabled` (agent/moa_loop.py: disabled preset ⇒ empty reference fan-out, aggregator acts alone).
- **Probe-verified wire flags are exactly as broad as the probe:** per-profile flags like `model.reasoning_echo` apply to the profile's CURRENT provider — enabling fleet-wide off one provider's probe risks 400/422 on strict providers that reject echoed fields, and «accept+ignore» providers gain pure token weight with zero benefit. Enable only where a live probe proved accept AND honour. DashScope facts (probed): qwen3.8-max honours reasoning_content echo; kimi-k3 ignores it; zai/glm and openai-codex unverified → keep off. Details in `references/harness-efficiency.md`.
- **Kernel releases silently re-inflate the static footprint** (observed: tools 41→52, system prompt ~2× after a release lane) — re-run `hermes prompt-size --json` after every release before claiming trim/deferral levers are still applied.
- **fleet-policy:** direct sqlite reads of kanban.db and the sessions dir are blocked — use `kanban_*` tools and `hermes sessions ...` CLI. Read-only `mode=ro` queries on `state.db` pass.
- **`hermes skills list` truncates names** to ~20 chars with `…` — never join audit data against that output. Walk skill dirs on disk and read frontmatter `name:`/`description:`; when matching the installed set, treat `…` as a prefix match.
- **Skill usage audit:** count actual `skill_view` calls in `messages.tool_calls` over N days across ALL profiles (script: `scripts/skill_usage_audit.py`), normalize `category/name` and `category:name` forms to the base name, and cross-check disk frontmatter names (folder renames happen).
- **Duplicate skill copies across dirs** (global `~/.hermes/skills` + per-profile `profiles/<p>/skills`): they do NOT stack token cost within one prompt (each profile loads only its own tree) — so disabling via config is sufficient for tokens; deleting duplicate files saves disk only. Compare by SHA-256 of SKILL.md before touching anything; several identical pairs exist with byte-different variants (company-side usually the edited one).
- **Tiering the disable list:** safe = legacy of deleted projects + never-loaded heavy packs (creative/productivity/rampstack); hold back = recently installed packs the owner chose + "dormant insurance" skills likely needed soon (pdf, xlsx, google-workspace). Present tiers and get explicit approval per tier before disabling.
- `hermes config set skills.disabled '[...]' --force` — the flag only suppresses the unknown-key notice; `skills.disabled` IS a read key (consumed by skill_utils), so the list works despite the warning.
- **Skill body size is a per-load cost** — every `skill_view` injects the full SKILL.md into context. Keep only always-on rules in SKILL.md and move depth into on-demand `references/`; when auditing tokens, inspect the largest SKILL.md files in the profile (one slimming pass can cut ~80% of chars without dropping any rule). Rank skills by weekly injection = loads × chars/4, not by load count alone — one 150KB SKILL.md loaded 160×/week is ~6M injected tokens before re-sends; split top products into a ≤3.5KB always-on core + references/.
- **Skill reload loop after compression:** context compression prunes loaded skill bodies (`[SKILL_PRUNED]` markers) and the agent re-loads them via `skill_view` — in long sessions this reaches hundreds of loads of one skill. Detect via same-args `skill_view` counts per session (≥6 suspicious, ≥50 a loop) — but FIRST dedupe tool_calls rows by call_id: state.db stores duplicate rows for identical calls and inflates raw same-args counts up to ~9×, so a moderate reload pattern can look like a loop and a «419×» claim can be a 68-unique-call artifact. insights "Top Skills" loads hide this because they aggregate across sessions. Cure = slim SKILL.md bodies + short-lived sessions, never more reloading.
- **Error turns are a token multiplier:** every failed tool call costs a full context re-send on retry. Classify tool-result errors by distinct pattern per profile (policy blocks incl. false-positive guard hits on safe commands, schema misuse like missing completion summary, wrong flag types, missing task_type markers, same_failure_loop, timeouts) and fix the top patterns — a 10% error rate on 150k weekly tool results is ~15k wasted turns.
- **CLI run pitfalls:** `hermes insights` can take minutes on a large state DB — redirect to a file with a 600s timeout, don't pipe through head at default timeout. Never share scratch files via `/tmp` between terminal (MSYS) and execute_code (Windows python) — resolve an absolute Windows scratch path in the same call, or rerun the CLI inside a python subprocess (shell=True) and parse stdout in one call. Filter `Config ref ...` warning lines before parsing. Parse box-table output (cron list) with a stateful python line parser; grep/paste column joins break on box-drawing chars.
- **Verify after changes:** application varies per key — «NEW sessions only» is not blanket-true (UPDATE 2026-10-03: the official configuration snapshot in the evidence root documents gateway hot-reload of compression/context length; verify the installed consumer for the specific key); re-run `hermes insights` after 2–3 days to confirm the delta. Gateway restart is not required but kills live sessions — ask first.
- **Test-fires can fail for unrelated reasons:** a manual cron test-run failed on provider HTTP 429 (rate limit), not config — don't read a failed test-fire as proof a change broke; judge config by readback + the next scheduled run.
- **Desktop GUI automation is a context bomb:** `computer_use`/accessibility-tree inspection returns thousands of nodes into the conversation — one dump of a settings/board window can exceed an entire task's budget, and the owner treats it as «тратит токены в пустоту» whenever the same action had a native tool or CLI path. Route lifecycle/board/config actions through `kanban_*` tools and CLI first; use GUI automation only for genuinely visual work, and never to hunt for a button.
- `rtk init -g --agent hermes` (rtk CLI present on this host) advertises automatic command-output token savings; unverified in this fleet — evaluate before enabling, don't promise it.
