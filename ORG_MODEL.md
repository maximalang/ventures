# ORG MODEL — как устроена автокомпания (канон 16.09.2026)

Директива владельца 16.09: флот управляет и развивает ВСЕ отделы и проекты; направления — отдельные коллективы агентов; видео-задачи всех продуктов идут через один видео-отдел; всё должно быть качественно и просто, без каши и лишних сложностей.

## Два типа досок (всего 2 типа — больше не вводить)

| Тип | Что это | Доски сейчас |
|---|---|---|
| **Отдел (функциональный)** | Один коллектив агентов, обслуживающий ВСЕ продукты по своей функции | `video`, `freelance` |
| **Продукт (проектный)** | Один продукт/венчур со своей выручкой и метрикой | `recruiter-radar`/`rr-team`, `seo-site` |

Плюс контуры управления: `portfolio` (стратегия, капитал, GO/NO-GO), `fleet-ops` (общие аккаунты, модели, инфраструктура), `general` (разовое), `venture-lab` (бэклог идей до регистрации продукта).

## Правило маршрутизации задач (единственное правило)

**Задача идёт на доску того, ЧТО делает работу, а не того, для какого продукта она делается.**

- Нужен клип/видеоролик/видеомонтаж — для RR, для seo-site, для своего канала или для заказчика → доска `video`.
- Нужен заказ с фриланс-площадки (сайт, бот, интеграция, парсинг) → доска `freelance`.
- Нужна фича/фикс/деплой конкретного продукта → доска этого продукта.
- Нужен общий аккаунт/модель/capability/инфраструктура → `fleet-ops`.
- Идея без регистрации продукта → `venture-lab` (бэклог).
- Выбор «вкладываем капитал сюда, не туда», GO/NO-GO, новая бизнес-архитектура → `portfolio`.

Если задача касается двух мест (например «видео для лендинга RR»): **исполнение на `video`**, а продуктовая приёмка/метрика — карточкой на доске продукта, связанной как родитель. Никаких дублей исполнения.

## Отделы

### video (Video Department)
Клиппинг Klipni (наёмные нарезки), контент-каналы, B2B «клиппинг под ключ», видеопродакшн для продуктов флота. Метрика (проект): `paid_clips_approved_28d`. Движок: autoclip v1.2.1 (MIT, MCP+CLI, faster-whisper RU). Обязательный QA-гейт перед публикацией (правило Klipni: полностью ИИ-сгенерированный ролик не принимают — нужна человеческая/флотская редакция поверх).

### freelance (Freelance Department)
Автономный конвейер: мониторинг заказов → скоринг → отклик → исполнение tech-воркерами → сдача → отзыв. Метрика (проект): `paid_orders_delivered_30d`. Границы: только отклики на открытые заказы (никакого холодного спама — mass outreach = класс эскалации владельцу); аккаунт площадки = личность владельца; первые заказы с финальным approve владельца.

### Новые отделы — только по триггеру
Отдел создаётся, когда по функции идёт **поток повторяющихся задач из ≥2 источников** (продуктов/заказчиков). Пустые доски не создаём. Кандидаты на будущее: `marketing`, `support`, `content`.

## Специалисты отделов (профессиональные роли)

**Канон (устраняет противоречие с универсальным ростером):** базовый состав флота — универсальные продуктовые роли из `OPERATING_SYSTEM.md` (`company`, `tech`, `product`, `design`, `ux`, `qa`, `sales`, `finance`, `research`, `operations`); они обслуживают ВСЮ продуктовую работу. Специалист-профили существуют **только в общих отделах** (`video`, `freelance`) и создаются **только по evidence-триггеру** (протокол ниже). Спец-профиль — это дополнение к универсальному ростеру, а не второй параллельный состав; он никогда не заменяет универсальные роли в продуктовой работе и не входит в универсальный ростер.

Директива владельца 16.09: в спецотделах работают **спецагенты-профессионалы**, а не универсальные ИИ-агенты. Результат должен быть реально профессиональным.

**Специалист = отдельный Hermes-профиль** со своей профессиональной идентичностью (SOUL.md с ремесленным знанием), куратом профильных скиллов и закреплённой моделью под класс задачи. Диспетчер канбана спавнит его по имени `assignee`. Это НЕ тяжёлый резидентный процесс — ленивый запуск (воркер поднимается на задачу и гаснет).

### Профессиональный ростер video-отдела (lean-ядро, 16.09)

| Профиль | Роль | Модель | Отвечает за |
|---|---|---|---|
| `video-director` | Режиссёр коротких форм | gpt-5.6-sol (креатив/смысл) | хук, выбор момента, структура истории, ритм, режиссёрское задание монтажёру |
| `video-editor` | Монтажёр / пост-продакшн | glm-5.3-flash (техника) | сборка по реж.заданию, кадрирование 9:16, субтитры, звук (loudnorm), экспорт, provenance, preflight |

Разделение труда = разделение из QUALITY_STANDARD.md: режиссёр owns раздел B (редакторское качество/смысл), монтажёр owns C/D/E (субтитры/аудио/экспорт), независимый `qa` ставит `gate:qa=pass` (ни режиссёр, ни монтажёр не оценивают свой клип).

**Звукорежиссёр, колорист, моушн-дизайнер — НЕ созданы заранее.** Добавляются по необходимости (см. протокол ниже), когда пилот покажет, что конкретный дефект системно валит модерацию и его нельзя закрыть в рамках editor-роли.

### Ростер freelance-отдела
Пока исполняют общие роли `tech`/`qa`/`research` под управлением конвейера. Спецы (например `frontend-pro`, `parser-pro`) создаются по триггеру, когда конкретный класс заказов станет потоком и потребует глубокой экспертизы.

## Протокол создания агентов и отделов (по необходимости)

Директива владельца 16.09: доп. агенты в отделах И сами отделы создаются **флотом автономно из необходимости** — для повышения качества при расширении или под новые проекты (пример владельца: «агента поддержки добавить в будущем, если нужен будет»). Не заранее, не «на вырост».

**Триггеры создания НОВОГО спецагента (любой один):**
1. Системный дефект качества: один и тот же класс брака ≥3 раз валит гейт/модерацию, и его нельзя устранить в рамках существующей роли.
2. Поток работ: устойчивая очередь задач одного узкого ремесла из ≥2 источников, которая тормозит из-за отсутствия экспертизы.
3. Новый проект/продукт требует профессии, которой в пуле нет.
4. Расширение: текущий специалист перегружен и деградует качество (WIP-лимит исчерпан, реwork-циклы растут).

**Процедура (делает company или отдел autonomously, 0 ₽, без владельца):**
1. Зафиксировать триггер evidence'ом (метрика/дефекты/очередь) в карте-обосновании.
2. `hermes profile create <role> --clone-from <ближайший по модели> --no-alias` → написать профессиональный SOUL.md (ремесло, цикл, границы, handoff, Fleet Policy Gate) → `hermes profile describe <role>` → закрепить модель под класс задачи.
3. Курировать скиллы-плейбуки профессии (`hermes --profile <role> skills install …`), верифицировать `skills list`.
4. Занести роль в ростер отдела в этом файле + в `company-os` skill.
5. Пробный прогон на реальной задаче под наблюдением; если качество не выше базовой роли — откатить (профиль удалить), триггер признать ложным.

**Откат/удаление:** роль, не оправдавшая себя за 2 цикла, удаляется (`hermes profile delete`), её задачи возвращаются базовой роли. Анти-каша: ростер раздувать нельзя — каждый спец должен доказывать, что он лучше универсала.

**Создание НОВОГО отдела** — тот же принцип, но триггер жёстче: поток повторяющихся задач одной функции из ≥2 источников (продуктов/заказчиков). Пустые доски не создаём. Кандидаты: `marketing`, `support`, `content`. Решение о новом отделе = `decision:company=go` + правка этого файла.

## Управление (кто что решает)

- **company (CEO)**: приоритеты между отделами и продуктами, распределение капитала/времени флота, `decision:company=go|nogo`, создание/закрытие отделов.
- **Отдел/продукт**: своя операционная работа по outcome loop (метрика → одна маленькая обратимая ставка → исполнение → независимая верификация → поставка → наблюдение → continue/kill/iterate).
- **Роли флота** (research/tech/qa/finance/operations/product/design/ux/sales) — общий пул специалистов; отдел не «владеет» ролями, он их нанимает под задачу.
- **Владелец**: серьёзные классы эскалации (юридическое, владение/root access, массовый outreach, необратимые данные, бюджет сверх мандата) + всё, что привязано к личности (аккаунты, самозанятость, карты).

## WIP-лимит (анти-каша)

Не больше **5 параллельных воркеров** и **одна активная ставка на отдел/продукт**. Остальное — в todo, не в работе. Если отдел хочет вторую параллельную ставку, он сначала закрывает или ставит kill-критерий первой.

## Анти-паттерны (запрещено)

1. Дублировать исполнение одной задачи на двух досках.
2. Создавать доску «на будущее» без потока задач.
3. Держать задачу в работе без kill-критерия.
4. Писать орг-правила в комментариях карточек вместо этого файла.
5. Вводить третий тип доски/сущности без решения владельца.
